# Rentlo Project Overview

## 1. Product Summary
Rentlo is a zero-brokerage property discovery platform initially focused on the Hubli-Dharwad region (with the infrastructure ready for multi-city expansion). Internal or external agents list properties securely, and prospective buyers can browse properties for free. To access exact coordinates and the property owner's direct contact details, buyers pay a small fee (e.g., ₹10, dynamically driven per city) to unlock the listing.

## 2. Roles and Responsibilities
Access control is strictly enforced server-side using Django REST Framework permission classes (e.g., `IsAdmin`, `IsAdminOrModerator`, `IsAgent`).

- **Admin (`role='admin'`)**: Has global access. Can view analytics, manage commission rules, mark earnings as paid, view fraud flags, and perform all moderator and agent duties.
- **Moderator (`role='moderator'`)**: Can access the moderation queue to approve, reject, or flag potentially fraudulent properties. They ensure listing quality before properties go live.
- **Agent (`role='agent'`)**: Creates new property listings, restricted strictly to their `assigned_cities` (enforced server-side). They have a dashboard to track the status of their listings and view their own approved/paid earnings.
- **Buyer (`role='buyer'`)**: Can browse public (live) properties for free with location data masked. They initiate payments via Razorpay to unlock exact locations and owner phone numbers.

### Core Data Models

1. **User**: Handled by custom user model. Contains roles (`admin`, `moderator`, `agent`, `buyer`), phone number, and a many-to-many relationship (`assigned_cities`) to restrict agents/moderators to specific operating regions.
2. **City / Locality**: Hierarchical geographic structure. A `City` dictates the exact `unlock_price` for that region. `Locality` ties directly to the property.
3. **Property**: Core listing data (coordinates, owner details, price, type, status). Status dictates visibility (`draft`, `pending_review`, `live`, etc.). Includes computed fields like `is_verified` and `trust_score`.
4. **PropertyMedia**: Associated images for a property. Automatically optimized into WebP format with `medium_url` and `thumbnail_url` generation via background pipeline to Cloudflare R2.
5. **Unlock**: Transaction record tying a Buyer to a Property. Initially `pending` until Razorpay webhook confirms payment.
6. **Feedback**: Captured post-unlock from buyers to rate listing accuracy, aggregating into public `trust_score`s for properties and agents.
7. **CommissionRule**: Defined by admins per city or per specific agent. Dictates the payout structure (flat fee or percentage).
8. **EarningEntry**: Automatically generated on specific triggers (moderation approval or unlock success) based on the active `CommissionRule`. Can be bulk updated to `paid` by admins.
9. **Notification**: In-app notifications generated by system events (e.g., listing approved, fraud flagged).

## 4. Core Workflows

- **Listing Creation**: Agents submit property details -> Owner receives an OTP -> Agent enters OTP to capture consent -> Listing goes to the Moderation Queue.
- **Moderation**: Moderators review pending listings. If approved, the listing goes `live` for 30 days and an `EarningEntry` (pending) may be auto-generated based on active `CommissionRule`s. If rejected, a reason is required. Agents can also be flagged for fraud.
- **Buyer Browse & Unlock**: Buyers browse live listings with coordinates masked (e.g., offset slightly). To unlock, they click the unlock button. If unauthenticated, an inline OTP modal verifies their phone number and auto-creates a buyer account (skipping standard signup). A Razorpay order is generated, configured to prioritize UPI and prefill the verified phone number. Upon successful payment, a webhook updates the `Unlock` record, and the exact coordinates and owner phone number become accessible. An unlock commission may also be generated for the listing agent.
- **Listing Lifecycle**: Properties expire after 30 days. Agents receive notifications to reconfirm them.
- **Earnings Tracking**: Dormant by default. If a `CommissionRule` is active for a city or specific agent, `EarningEntry` rows are silently created during moderation approvals or unlock webhook events. Admins can bulk mark these as paid.

## 5. System Architecture
- **Client Apps**:
  - `buyer-web`: React (Vite) frontend for public buyers, configured as a Progressive Web App (PWA) with Service Worker offline caching. Features Server-Side Injection via Django (`PropertySEOView`) for `/property/<id>` routes. This guarantees that search engines and WhatsApp link previews can scrape the OpenGraph tags and raw HTML property data without executing JavaScript.
  - `admin-portal`: React (Vite) frontend for Admins, Moderators, and Agents. Accessible only to `admin`, `moderator`, and `agent` roles. Uses JWT stored in HTTP-only cookies.
- **API Layer**: Django REST Framework (DRF) serving JSON APIs at `/api/v1/`.
- **Database**: PostgreSQL (or SQLite for local dev), accessed via Django ORM.
- **File Storage**: Cloudflare R2 for storing property images and consent proofs securely via S3-compatible APIs. Images are processed natively by the Django backend using Pillow to auto-generate WebP thumbnails and medium formats.
- **Payment Gateway**: Razorpay for handling unlock transactions and webhooks.

## 6. Known Expansion Hooks
- **Background Jobs**: Celery with Redis for asynchronous tasks (e.g., expiry checks, notifications).
- **Deployment Structure**:
  ```text

  ├── buyer-web/          # React SPA (Buyer)
  └── backend/            # Django project
      ├── accounts/       # User and auth logic
      ├── analytics/      # Admin dashboard metrics
      ├── earnings/       # Commission rules and ledger
      ├── media/          # Cloudflare R2 uploads
      ├── moderation/     # Approval/Rejection queue
      ├── notifications/  # Alerts system
      ├── properties/     # Core listing and location logic
      └── unlocks/        # Razorpay integration
  ```

## 6. Environment Variables Required

**Backend (`backend/.env`)**:
- `SECRET_KEY`: Django secret key for cryptographic signing.
- `DEBUG`: Boolean to enable/disable debug mode (False in production).
- `ALLOWED_HOSTS`: Comma-separated list of allowed domains.
- `DB_ENGINE`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`: PostgreSQL connection details.
- `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`: Razorpay API credentials.
- `RAZORPAY_WEBHOOK_SECRET`: Secret to verify incoming webhooks from Razorpay.
- `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, `R2_ENDPOINT_URL`, `R2_PUBLIC_URL_PREFIX`: Cloudflare R2 configuration for media storage.

**Frontend (`admin-portal/.env` & `buyer-web/.env`)**:
- (Typically uses proxying or hardcoded base URLs in dev, but in production requires API URL mapping, e.g., `VITE_API_URL` pointing to the backend).

## 7. Current Status
- **Built & Tested**: Multi-role authentication (JWT), hierarchical locations (City -> Locality), property listing flow with OTP consent, moderation queue with fraud tracking, Cloudflare R2 image uploads, Razorpay unlocks and webhook handling, dynamic analytics dashboard, and the earnings tracking layer.
- **Pending/Future**: Full production deployment pipeline (CI/CD), integration of actual SMS provider for OTPs (currently mocked/logged), automated Celery beat setup for daily cron jobs in production environment.

## 8. Expansion Plan
The architecture is inherently built for scale without code changes:
- **Locations**: Adding a new city is a simple database row insertion. All frontend dropdowns and backend logic dynamically query `City` and `Locality` models.
- **Pricing**: Unlock prices are tied to the `City` model, allowing different markets to have different pricing out of the box.
- **Commissions**: The `CommissionRule` model allows granular per-city or per-agent payout structures. You can onboard external agents in a new city and activate a specific commission percentage for them instantly via the Admin Portal, while keeping internal agents on a different (or zero) commission structure.
